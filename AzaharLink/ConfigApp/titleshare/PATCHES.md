# Patches to the title delivery module

`common/` and `source/` here are the files of the original experiment (the project in `../TitleShare`, which is never modified), taken
as they were, **plus the thirteen patches below and nothing else**. The scheduler, the receiver's logic, the store, the CIA
builder and the crypto are the original code. Six patches change only a place where the module named a folder or a file of its own, a text the
user sees, or the logging layer; the two on the sender (`sender.c`, `sender.h`) were asked for by the user after the third hardware test and
change what the sender shows and how it welcomes a console that joins while it is sending; three more (`common/proto.c`, `common/proto.h`,
`source/receiver.h`, with a few lines of `receiver.c`) add a **trailer to the ROSTER frame** so that every receiver can show who the other
receivers are and what they are doing. The trailer is after the entries the frame already had: a receiver of the older build reads the frame
as it always did (it only checks that the entries are there), and a new receiver that gets a frame without the trailer (an older sender) shows
"Receiver N" and no state. Nothing else of the protocol changes: the manifest, the data and the acknowledgements are as they were.

`Tests/titleshare_vendor_check.sh` proves it on every run of `Tests/policy_check.sh`: `MANIFEST.md5` is the copy as it is,
`ORIGINALS.md5` is the md5 of every original file, `vendor.patch` is the unified diff original -> copy, and the copy minus the patch has
exactly the originals' md5 (where `../TitleShare` exists, the originals are compared too and the patch is applied to them). Only the thirteen
files below may be patched. `Tests/titleshare_vendor_make.sh` regenerates the three files after a patch is edited.

**What is built.** The module's own text screens (`source/main.c`, a console menu) are vendored whole but **not built**: 3DS Link draws the Titles Delivery screens itself (citro2d, English) and reaches the module through `../titleshare_host/delivery.[ch]`, which calls `sender.c`, `receiver.c`, `catalog.c`, `ctx.c` and `power.c` as they are. The patch to `source/main.c` below is kept (the file is still the original plus that text patch, as the proof requires).

The module now takes everything the app decides from setters the app calls before the module runs
(`../titleshare_host/hostcfg.h`: the app's folder and data folder, the boot9.bin the app found, the log switch). The names and the
rotation of the log are in `../titleshare_host/logrot.h` (pure functions with unit tests). Both files are the app's, not the original's.

| file | what the patch does |
| --- | --- |
| `source/ctx.c` | `boot9.bin` is the one the app found (`hc_boot9_path()`), not one of three fixed places; the `movable.sed` fallback looks next to the app, then in GodMode9's folder (`hc_movable_candidate()`), not in `sdmc:/3ds/TitleShare/`; the message of a missing key file names no folder. |
| `source/catalog.c` | The cache of the titles' names is `catalog.cache` in the app's data folder (`hc_data_path()`), not `sdmc:/3ds/TitleShare/catalog.cache`; without a data folder it is neither read nor written. (2026-10-19) When AM refuses the versions of all the titles in one call (one broken title, left by an interrupted installation, makes it refuse the whole list, and without versions every icon was read again at every start) the versions are asked title by title, and only the titles AM cannot describe stay out of the cache (`verBad`); the log's `versioni_AM` says how many. |
| `source/receiver.c` | The folder of the temporary files of a title being received is `park` in the app's data folder, not `sdmc:/3ds/TitleShare/park`; the form of its path for the file system service is made from it (`hc_sd_relative()`). (2026-10-19) When the installing thread is stopped in the middle of a title (the user cancelled, the sender went away, the system asked to close) the open installation is cancelled AND what AM already holds of that title is taken away with `scrub_failed` (title, ticket, pending import), as after a failed write: before, the half title stayed in the system's list, unusable, and slowed every scan. The title's result is an error with the code `0xC8604C03` ("stopped before the end"), which the app's result page says in words. |
| `source/log.c` | The log is switchable and rotating: with the app's Debug log off no file is created and no thread started (`ts_log()` costs nothing); on, it is `3DSLink-TitleDelivery.log` in the data folder, appended to, 64 MiB a file, older ones `.1.log` ... `.7.log` (8 files at most, the plan is `logrot_plan()`); the old `log.txt` / `log-prev.txt` renaming and the 16 MB cap are gone; the first line of the file no longer names TitleShare. (2026-10-17) `ts_log_active()` says whether the log is open, so that code that needs system calls to write a line (the "sistema" line) can skip them with the Debug log off. |
| `source/log.h` | The comment describing the above (no code). |
| `common/proto.h`, `common/proto.c` | `ts_roster` has `ext` and three arrays (`node`, `state`, `down`); `ts_pack_roster` writes them after the entries (one byte with the number of receivers, then three bytes each: the UDS node the receiver speaks from, what it is doing, how much it has downloaded) and `ts_unpack_roster` reads them when the frame is long enough and the count matches (else `ext = 0`). The frame stays far below the size of one UDS frame (16 receivers: 28 + 128 + 49 bytes). (2026-10-17) `TS_F_ERR` (flag 4 of an ACK2: finished, but a title failed) and the two new states of the trailer, 5 (waits for its turn) and 6 (finished with errors), in the comments. |
| `source/receiver.h`, `source/receiver.c` | `ts_recv_stats` has `otherNode`, `otherState`, `otherDown` next to `otherCursor`, filled from the roster's trailer (`otherState` 255 = not known). The app turns a node into the name of the console. **(2026-10-17, after the second hardware test)** (1) What a title that failed in AM leaves is taken away: after a refused write, an unreadable park file or a refused end of the install the writer thread deletes THAT title, its ticket and a pending install (`scrub_failed`; never the game it belongs to): a failed DLC used to stay on the console (0.4 GiB) and the app then called it "already installed". (2) An acknowledgement that says "finished" also says `TS_F_ERR` when a title failed, so the sender can show "finished with errors" (an older sender does not read the flags of an acknowledgement). (3) The messages: "all downloaded: installing" instead of "waiting: the sender is serving others" when nothing is missing any more (the old text was shown for 261 s on a console that was only installing); when the search for the room finds it and the beacon says it is full, "stanza piena (n/m): riprovo (N s)"; the seconds count from the real drop; `reconnects` counts the rejoins that worked, not the attempts; the log line of the end says why the session ended. (4) `receiver_describe` gives the whole name of the first title (the beacon's new `firstName`; an older sender's 15 characters get "..."), the room's Wi-Fi channel and how many receivers are in it of how many it takes; the stats carry the channel, the free space of the card as the parking thread read it (the screen no longer reads the card itself) and `reconnecting` (the host asks no names of the wireless service while the search for the room runs: both use the same service session and the screen froze for 10 s once). (5) A failure that is not AM's (the seed that is added after AM finished) does not take the title away: it is installed, as before, and reported as an error; the cleanup also beats the watchdog. (6) The count of bytes of the title that installs is reset before the next title is chosen. |
| `source/net.h` | The dead constants are gone (`TS_SILENCE_MS`, `TS_CLIENT_TIMEOUT_MS`, `TS_PAUSE_MAX_MS`: nothing used them and their comments were false), `TS_NET_NODES` (8: the sender and seven receivers) names the nodes of the network, and the beacon's `ts_appdata` has `firstName` (the whole name of the first title) after the 29 bytes it always had: an older receiver reads only those, a new receiver that gets a short beacon (an older sender) falls back to the 15 characters. |
| `source/power.c` | The state of the shell (lid) is asked in a thread of its own (`power_thread`) and the periodic "sistema" log line (Debug log on only) in another (`sys_log_thread`: it asks the card and the wireless service and can wait seconds, the lid polling must not wait with it), not in the interface's loop: the interface only reads the result. The "sistema" line costs nothing with the Debug log off (it used to make ~10 system calls every 30 s anyway). A call to the system that takes 300 ms or more (`aptMainLoop`, the shell state, `udsGetChannel`, the periodic line) is written to the log: once the interface froze for 10 s while the receiver looked for the room again and the log could not say in which call. |
| `source/sender.h` | `ts_sender_stats` has nine more arrays for the sender's screen (name and UDS node of each receiver's console, what it wants, per title downloaded and installed, the blocks it has downloaded and installed, free space, efficiency), and the declaration of `sender_set_room_estimate()`. Read-only data: nothing the sender decides depends on it. |
| `source/sender.c` | (0) The roster's trailer is filled with each receiver's node, state and downloaded share, and the room's share and time are the app's when it gives them (`sender_set_room_estimate()`; the module's own figures are the default). (1) A table token -> UDS node (filled when a READY arrives, and again with every acknowledgement; cleared when a room starts) so that `progress_fill` can put the receiver's console name (its UDS user name) and the per-receiver details of `sender.h` in the stats; a node that is no longer in the network gets no name. **(2026-10-17, after the second hardware test)** The name of a receiver's console is **remembered by token** (the last good one: a lookup that fails for a moment no longer turns it into "Receiver N", and a receiver that stops answering keeps its name until it leaves the room); the node of a silent receiver is still told to the others while it is in the network and no other receiver claims it; a receiver heard just now that has no name is explained once in the log (token, node, answers of the system). Two new states in the roster and in the stats: 5 = it still needs blocks but not of the title that is being sent (waits for its turn), 6 = finished with a title that failed (`TS_F_ERR`). The room's Wi-Fi channel is read once the room exists, the beacon carries the first title's whole name, the room line of the log says seven receivers (it said eight, which is the table's size, not the limit). (2) `send_ctl()`: every control frame (manifest, state, roster) tries again while the radio queue answers "busy" (about 40 ms at most): with the queue full of blocks they used to be dropped without a word, so a console that had just joined waited a long time for its list and the receivers saw the roster every three seconds instead of every second. (3) When a new node appears in the network (checked every 100 ms) the manifest is sent every 200 ms for 1 s, i.e. five times (the second starts again for every new node; the normal repetition, every second, goes on after it) and the blocks stop for 500 ms (at most once every 2 s, so that several consoles joining one after the other cannot stall the room), so that a console that joins a room that is already sending gets the list at once. The scheduler, the choice of blocks and the protocol are untouched. |
| `source/main.c` | The menu says `3DS Link - Title delivery` where it said the old name (three titles of its screens); the hint for a missing key file no longer names a folder. Its Italian texts are otherwise the original's. |
| `common/sdcrypt.c` | The constant of the key generator (the one the SD key and the NCCH key are scrambled with) is not written in the file: `sd_derive_key` and `ncch_scramble` ask `bk_get(BK_GENERATOR_CONSTANT, ...)` of the app's `titleshare_host/builtin_keys.h` (the value Azahar ships as `generatorConstant`, carried there obfuscated with a key of zeros, like Azahar's `default_keys.h`). `sd_derive_key` has a new result, -9, for a blob that is not what it should be. |

Not changed on purpose: the comments and the identifiers of the original that mention its old name (nothing the user sees), the wireless
protocol (its network names and ids), and every file of `common/` except `proto.c`, `proto.h` and `sdcrypt.c`. **In this public copy** the original of `common/sdcrypt.c` is not given (its text carries a constant that is not written in this repository, only obfuscated in `titleshare_host/builtin_keys_blob.h`): there is no hunk of it in `vendor.patch`, and `ORIGINALS.md5` records this copy of that one file.
